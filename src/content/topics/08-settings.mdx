## なぜこのトピックが大事か

トピック⑦で「個人情報は AI に入れない」と書きました。とはいえ、業務上どうしてもグレーゾーンの情報を扱う場面はあります。そこで効くのが **「契約形態」** と **「設定」** の二段構え。

> **「設定でオフ」と「契約で対象外」は別物。** どちらも揃って初めて、施設の業務利用に耐えうる環境になります。

### 他のAIサービスをお使いの場合（参考）

本研修は Gemini を中心に進めますが、既に ChatGPT や Claude をお使いの方向けに要点だけ簡潔にまとめます。

- **ChatGPT**：Settings → Data Controls → 「Improve the model for everyone」をオフにすると、以降の会話が学習に使われなくなります（Business / Enterprise はデフォルトで学習対象外）
- **Claude**：2025 年 8 月の規約変更により、個人プラン（Free / Pro / Max）は**オプトアウト方式**（オフにしない限り学習対象、保持 5 年／オフなら 30 日）に変わりました。Settings → Privacy → 「Help improve our AI models」で変更できます（Team / Enterprise はデフォルトで学習対象外）

いずれも、業務利用・個人情報を扱う場面では **法人契約への切り替えを推奨**します（詳細は各社公式ヘルプを確認してください）。

## 法人プランが担保する「学習オフ」以外の価値

| 価値 | 内容 |
|---|---|
| **データ学習対象外（既定）** | 設定ミスのリスクがそもそもない |
| **SSO / SCIM**（統一ログイン／ユーザー情報自動同期） | アカウント管理を施設の ID 基盤に統合できる |
| **監査ログ** | 「誰が、いつ、何を聞いたか」を法人側で記録できる |
| **管理者権限** | 退職者アカウントの即時無効化、利用範囲の制限 |
| **データ保持期間の制御** | 0 日保持 / 30 日保持 等を選べる場合がある |
| **DPA（データ処理契約）** | 個人情報保護法上の委託契約として根拠を持てる |
| **ISMAP 登録**（一部サービス） | 政府・自治体の調達基準を満たす |

**福祉施設にとっての意味**：
- 「政府が事前にセキュリティ評価したリスト」に載っているサービスは、**説明責任を果たしやすい**
- 自治体との連携業務、行政との情報やり取りを含む場面で、**選定根拠として強い**
- 民間社会福祉法人でも、**「ISMAP 登録済を優先」** という内規を作ると、判断が早くなる

### 具体例早見表

| 入力しようとしている内容の例 | 分類 | Gemini in Workspace で入力してよいか |
|---|---|---|
| 一般的な案内文・チラシのひな形（個人名なし） | 匿名化情報 | ✅ 問題なし |
| 研修資料・マニュアルの下書き | 匿名化情報 | ✅ 問題なし |
| 施設名・職員の氏名 | 通常の個人情報 | ⚠️ 条件付きで可（DPA・同意が前提） |
| 利用者の氏名・住所・連絡先のみ | 通常の個人情報 | ⚠️ 条件付きで可（DPA・同意が前提） |
| 利用者の病歴・障害の状況 | 要配慮個人情報 | ❌ 非推奨 |
| 逮捕歴・犯罪の経歴 | 要配慮個人情報 | ❌ 非推奨 |
| ケース記録全般（病歴・生活歴等を含む） | 要配慮個人情報を含む可能性大 | ❌ 非推奨（個別に要配慮情報の有無を確認） |

> ※「生活保護の受給歴」そのものは個人情報保護法が列挙する要配慮個人情報の定義に直接該当するとは限りませんが、ケース記録には病歴・障害等の要配慮個人情報が併記されることが多く、実務上は要配慮情報に準じた慎重な取扱いが妥当です。個別の該当性判断は専門家にご確認ください。

### なぜ「日本国内処理」が要配慮個人情報では重要になるのか

ここまでの「ISMAP 登録の有無」とは別に、もう一つ重要な論点があります。**個人情報保護法 28 条「外国にある第三者への提供の制限」（越境移転規制、令和 2 年改正で旧 24 条から条番号変更）** です。

Gemini in Workspace はデータの処理地を「グローバル」「米国」「ヨーロッパ」からしか選べず、日本国内に固定できません。法 28 条は、①我が国と同等水準の個人情報保護制度を持つと認められた国、②提供先が日本の事業者と同等の体制を継続的に講じている場合、③その他の例外事由のいずれにも該当しない限り、**あらかじめ本人の同意を得る**ことを求めています。Gemini in Workspace の処理地（グローバル／米国／ヨーロッパ）がこれらの例外に該当するかは個別確認が必要で、該当しない場合は越境移転への本人同意が必要になります。

ISMAP 登録は「安全に守れているか」（法 23 条・安全管理措置）を担保するものであり、「そもそも海外で処理してよいか」（法 28 条・越境移転）とは別の話です。ISMAP 登録済みであっても、この 28 条の論点は自動的にはクリアされません。

## 実名データを扱う場合の 3 段階（2026 年 9 月時点）

「要配慮個人情報に使えないのは困る」というお気持ちはもっともです。個人情報保護法は大きく 2 つの独立した義務を課しており、**片方を満たしても、もう片方の違反は消えません。**

- **安全管理措置（法 23 条）**：データを守る仕組み。リージョン指定・認証方式・監査ログなど、**アーキテクチャ（技術）で解決できる**
- **取得・利用目的の適法性（法 17 条・18 条・20 条 2 項）**：そもそも扱ってよいか。同意書・委託契約・利用目的の公表など、**法務・組織対応でしか解決できない**

### Tier C（最も厳しい要件）での具体的な最適構造

要配慮個人情報を実名で扱う場合、2026 年 9 月時点で最も現実的なのは「既存の Google Cloud インフラは維持しつつ、テキスト生成・要約・音声文字起こしは AWS Bedrock に任せる」ハイブリッド構成です。**ただし AI OCR だけは例外** で、実機検証の結果、AWS Bedrock（Claude/Nova 系）は日本語 OCR の精度に弱点があることが分かったため、OCR 用途に限っては GCP 側で自前ホスティングする PaddleOCR を使う構成を推奨します。

- **Cloud Run（GCP・日本リージョン）** が利用者からの入力を受け付ける窓口
- 保存は **Firestore（GCP・データ保存）**
- AI OCR は **PaddleOCR（自前ホスティング、Cloud Run CPU・東京リージョン、低コスト）**
- テキスト生成・要約・音声は **AWS Bedrock / Transcribe**
- クラウド間の認証は固定パスワード不要の **キーレス方式**

データの保存・AI 処理とも常に日本国内に閉じます。AI OCR だけは精度上の理由で自前ホスティングに切り出し、それ以外の生成 AI 処理は AWS Bedrock へ、という役割分担です。

**なぜこの構成が今のところ最適と言えるのか（根拠）**：

- **ISMAP の登録構造**：Google 関連は「Google Cloud 本体」「Google Workspace」「Gemini Enterprise」が別々の登録番号を持ち、基盤が登録済みでも上位サービスは自動的には登録されません。「Google Workspace + Gemini」だけでは日本限定の処理は保証されない一方、「Gemini Enterprise」（別製品）は日本ロケーション指定が可能です。AWS は Bedrock・Transcribe を含む単一登録（[C21-0008-2](https://www.ismap.go.jp/csm?id=cloud_service_list)）で構造がシンプルです。
- **個別の AI モデルは別途登録不要**（2026 年 1 月確認）：[ISMAP 運営主体自身の公式見解（ポータル KB0011070）](https://www.ismap.go.jp/csm?id=kb_article_view&sysparm_article=KB0011070)により、クラウド事業者が自社の生成 AI 開発基盤（PaaS）を ISMAP 登録範囲に含めていれば、そこで動く個々のモデル（Gemini・Nova Pro 等）は別途登録不要と確認されています。
- **コスト構造**：[Google Cloud 公式ドキュメント](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash)によれば、Gemini 3.5 Flash 以降を日本リージョン（asia-northeast1）で使う場合、通常の従量課金（Standard PayGo）が使えず、[シングルゾーンの Provisioned Throughput（Google Cloud アカウント担当者への問い合わせが必須）](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/provisioned-throughput/purchase-provisioned-throughput)のみ対応です。[料金ページの計算例](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)では月額 $2,700 × GSU 数という試算が示されています。小規模な組織には現実的ではありません。AWS Bedrock（Nova Pro）は固定費なしの従量課金のままです。
- **日本語 OCR に限定した実機検証（非公開ベンチマーク）**：実際の日本語書類（旧字体異体字・簡体字類似漢字・事業所名の紛らわしいペア等）を使った実機検証では、**AWS Bedrock（Claude/Nova 系）は特定の漢字を再現性ある形で誤読する** 弱点が確認されました。一方、自前ホスティングの **PaddleOCR（PP-OCRv6、CPU 推論のみ）** は、東京リージョンの Cloud Run（CPU のみ・低コスト）上で Gemini 3.5 Flash とほぼ同水準の精度を達成できることも確認されています。この項目は社内の実機ベンチマークに基づくもので、公開されている一次情報へのリンクはありません。

**技術を固めても残る法務・組織対応（必須）**：

- 利用者への同意取得・プライバシーポリシーの改定（AI 処理を行う旨の明記）
- クラウド事業者との DPA（データ処理契約）締結
- 委託先（システム開発事業者）との NDA・業務委託契約
- 要配慮個人情報を扱う場合は、3 省 2 ガイドライン（厚労省・総務省・経産省）相当の組織的措置

> ※ 本セクションは 2026 年 9 月時点の公式一次情報（ISMAP ポータル・AWS/Google 公式ドキュメント）に基づく技術的整理であり、法的な最終判断は専門家にご確認ください。

## 今すぐできること・これから準備が必要なこと

### ✅ 今日からできること

- 案内文・マニュアル・一般的な文章生成など、**個人が特定される情報を含まない用途** では、今お使いの Gemini in Workspace をそのまま使い続けて問題ありません。
- 相談メモの下書き等、**病歴・生活歴・障害の状況等の要配慮個人情報を含まない** 場合に限り、氏名・住所・生年月日等を仮名（A 様、B 様等）に置き換えてから入力すれば、現状のツールのまま活用できます。「困ったら、まず匿名化してから」を職場のルールにするだけで、使える範囲はかなり広がります。
- ⚠️ **ただしケース記録・支援経過記録のように病歴・生活歴等を含む文書は対象外です。** 氏名を仮名に置き換えても、生活歴・病歴・状況の組み合わせから本人が推測できてしまう場合があり、要配慮個人情報のままである可能性が残ります（上記 Tier C に該当）。

### ❌ 正直に：今はまだできないこと

- 利用者の実名と病歴・生活歴等を **そのまま** Gemini in Workspace やその他の一般的な AI ツールに入力すること。
- 「今の契約・今のツールのまま」でこれを安全にクリアする方法は、2026 年 9 月時点では存在しません。ここは期待を持たせすぎないよう、はっきりお伝えします。

### 🏗️ 組織として計画的に準備すべきこと

要配慮個人情報を実名で扱えるようにするには、個人のスマホ設定のように「その場で解決すること」ではなく、**システム構築と契約整理を伴う一定規模のプロジェクト** として進める必要があります。

- Tier C 対応の技術基盤の構築（Gemini Enterprise 日本ロケーション、または AWS Bedrock 等を用いたハイブリッド構成）
- 費用感の見積もりと予算確保（固定費が発生する構成もあるため、事前の比較検討が必要）
- ISMAP 登録範囲の個別確認、クラウド事業者との DPA 締結
- 3 省 2 ガイドライン相当の組織的措置の整備（要配慮個人情報を扱う場合）
- 利用者への同意取得・プライバシーポリシーの改定

これらは技術・法務の両面にまたがる専門的な整理が必要で、片手間で進めるのは現実的ではありません。まずは **「誰が意思決定者で、いつまでにどの範囲を実現したいか」を組織内で確認する** ところから始めることをおすすめします。

- **「設定で学習オフ」と「法人契約で対象外」は別物、両方そろえる**
